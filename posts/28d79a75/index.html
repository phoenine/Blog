Helm Introduction

发表于2021-04-22|更新于2026-11-05|系统架构
|总字数:4065|阅读时长:17 分钟|浏览量:

一套微服务部署到 Kubernetes，通常要提交 Deployment、Service、ConfigMap、Ingress 好几类对象。开发、测试、生产各维护一份 YAML，镜像 tag 改一次要同步三个文件，回滚时还得翻出上一版清单。Helm 把这些资源收进一个可以版本化的 Chart，用 values 区分环境，再用一条命令完成安装、升级和回滚。

这篇按 Helm 3 的使用顺序整理，从安装和创建 Chart 讲到模板语法与 Release 管理。读完能独立写出一个带 values 的 Chart，把它装进集群，并在模板报错时知道先看哪里。需要一台能连上 Kubernetes 集群的机器，kubeconfig 已经配好。

1. 为什么需要 Helm

Kubernetes 的 API 是声明式的。部署一个应用，就是准备一组资源对象的清单，交给 API server。对象少的时候，kubectl apply 够用。服务多起来，清单文件跟着涨，同一套模板还要在开发、测试、生产之间改参数。开发用 1 个副本，生产用 5 个，镜像 tag、资源限额、环境变量也各不相同。复制三份 YAML 能跑，改一个字段要同步三处，漏改一次就可能出问题。

Helm 把这组资源对象和默认参数打成一个包，这个包叫 Chart。模板负责生成清单，values 负责提供参数，同一份 Chart 可以渲染出三套环境。安装时 Helm 还会记录这次部署的版本、参数和清单，后续升级、回滚、卸载都围绕这份记录进行。

Helm 常被叫作 Kubernetes 的包管理器。apt 装一个软件，Helm 装一个应用需要的全部资源对象，并且记得自己装过什么。

2. 核心概念和组件

Helm 里有四个东西会反复出现。

名称 说明
Chart 应用包，包含模板、默认 values 和 Chart.yaml 元信息
Release 一次安装产生的运行实例，同一个 Chart 可以装出多个 Release
Repository 存放和分发 Chart 的仓库，类似镜像仓库
Helm CLI 本地命令行，负责渲染模板、管理 Release 并和 API server 通信

Chart 是静态的包，Release 是安装后的运行实例。同一个 Chart 在 default 和 staging 两个 namespace 各装一次，就是两个 Release，升级其中一个不会影响另一个。Release 名在同一个 namespace 里唯一，跨 namespace 可以重名，这一点和 Helm 2 不同。

Repository 就是存放 Chart 的地方，自己搭或者用公共仓库都行。Helm 用 helm repo add 把仓库地址加到本地列表，之后就能按名字搜索和安装 Chart。

3. Helm 2 和 Helm 3 的差别

Helm 2 在集群里跑一个叫 Tiller 的服务端组件。Helm CLI 把渲染好的清单交给 Tiller，再由 Tiller 和 API server 通信。Tiller 通常带很高的权限，多租户集群里很难管住。Helm 3 把 Tiller 删了，CLI 直接读本地 kubeconfig 连 API server，模板渲染也在本地完成。

变化点 Helm 2 Helm 3
架构 需要 Tiller 服务端组件 CLI 直接用 kubeconfig 连集群
卸载 helm delete --purge helm uninstall
拉取 Chart helm fetch helm pull
查看 Chart 信息 helm inspect chart helm show chart
安装时的名字 不指定时自动生成随机名 必须指定名称或加 --generate-name
Release 记录 存在 Tiller 所在的 namespace 默认存在 Release 所在 namespace 的 Secret 里

命令名称调整了，helm delete、helm fetch、helm inspect 在 Helm 3 里仍然可用，分别指向卸载、拉取和查看。helm delete --purge 里的 --purge 被移除，执行会直接报错。

迁移旧 Chart 时注意 apiVersion，v1 的依赖写在 requirements.yaml，v2 写进 Chart.yaml 的 dependencies。老 Chart 在 Helm 3 下一般还能装，只是用不上 v2 的新字段。

4. 安装 Helm 3

Helm 3 只有一个二进制文件，常见安装方式有三种，挑一种顺手的。

从官方下载站取对应平台的压缩包，下面以 linux-amd64 为例。

上面这串里的版本号只是示例，实际以 Helm Releases 页面 为准。官方也提供一键安装脚本，适合在开发机或 CI 环境里快速装好。

macOS 用 Homebrew 更省事。

装完执行 helm version，只会打印客户端版本；install、upgrade 这类命令才会读 kubeconfig 里的集群配置。

5. Chart 的目录结构

新建 Chart 不用手搭目录，helm create 会生成一个能直接安装的示例。

生成的目录大致是这样。

几个路径的作用如下。

路径 作用
Chart.yaml Chart 的元信息，名称、版本、类型、依赖都写在这里
values.yaml 模板渲染的默认参数
charts/ 存放子 Chart 依赖
templates/ 模板文件目录，渲染出的 Kubernetes 对象都放这里
templates/NOTES.txt 安装完成后打印给用户的使用说明
templates/_helpers.tpl 存放可复用的子模板，不会直接渲染成资源
templates/tests/ Chart 自测用的测试模板
.helmignore 打包时忽略的路径

Chart.yaml 记录 Chart 的基本信息，helm create 生成的版本去掉注释后大致如下。

version 是 Chart 包版本，遵循语义化版本。改了模板就要升版本，发到仓库后同一个版本不能覆盖。appVersion 是应用版本，只用于展示和记录，不参与依赖解析。apiVersion 写 v2，这是 Helm 3 的 Chart 格式。type 默认是 application，library 类型只提供可复用的模板，不能单独安装。name 一般和目录名保持一致，description 写一句这个 Chart 做什么。

6. Chart.yaml 和依赖管理

Chart 依赖别的 Chart 时，直接在 Chart.yaml 里声明。requirements.yaml 是 Helm 2 和 v1 Chart 的写法，Helm 3 仍然兼容；v2 Chart 如果还放 requirements.yaml，会提示迁移到 Chart.yaml。

name 是依赖的 Chart 名，version 是版本范围，repository 是仓库地址。condition 用 values 里的布尔值控制依赖是否启用，tags 可以按组批量开关。这里的 9.x.x 只演示范围写法，实际版本以仓库里存在的版本为准，解析结果会记录在 Chart.lock 里。

更新依赖用这条命令。

Helm 会把依赖下载到 charts/，同时生成 Chart.lock。有 lock 文件时，helm dependency build 会按锁定的版本还原依赖，效果和 npm ci 类似。依赖的 Chart 也会带着自己的 templates 和 values，安装时一起渲染，子 Chart 的值可以用 mysql.enabled 这样的层级在父 Chart 的 values 里覆盖。

7. 模板和 values

7.1. 模板渲染是怎么发生的

模板渲染可以拆成三步。Helm 读取 templates/ 下的模板和 values.yaml，执行模板里的 {{ ... }} 表达式，把渲染结果提交给 Kubernetes API server。

在 templates/ 里新建 configmap.yaml，先写一个不带模板表达式的版本。

这个模板没有写任何表达式，装第一次没问题，在同一个 namespace 里装第二次会报资源已存在。

解决办法是把资源名和 Release 绑在一起。

.Release 是 Helm 注入的对象，.Release.Name 是本次安装的 Release 名。安装时指定什么名字，渲染结果就用什么名字。同一个模板，装两次会得到两个不同名字的 ConfigMap。

7.2. 用 values 提供参数

把可变的值挪进 values.yaml，模板从里面取，Chart 就具备多环境复用的能力。

模板里通过 .Values.name 引用。

安装时可以用 -f 指定额外的 values 文件，也可以用 --set 临时覆盖。优先级从高到低是 --set、-f、Chart 自带的 values.yaml。多个 -f 同时出现时，后面的文件覆盖前面的。

7.3. 安装和检查

在 Chart 目录的上一级执行安装。

helm get manifest 输出的是渲染后的完整 YAML，排查问题时比盯着模板文件猜更直接。

安装前先渲染一遍，能省掉不少来回。

--dry-run 会走一遍安装流程但不提交资源，输出里有合并后的 values 和最终清单。helm template 只把渲染结果打到标准输出，适合放进 CI 做 diff。默认的 --dry-run 只做客户端渲染，helm template 也不连集群，lookup 这类依赖实时查询的函数拿不到数据；Helm 3.13 之后的 --dry-run=server 会连集群做校验，lookup 能读到真实资源。

8. 模板内置对象与流控制

8.1. 内置对象

模板里常用的内置对象有这些。

对象 内容
.Release 本次部署的信息，名称、namespace、Revision、是否升级
.Values values.yaml 和用户覆盖值合并后的参数
.Chart Chart.yaml 的内容
.Subcharts 访问子 Chart 的 Values、Chart 和 Release 作用域
.Files Chart 内普通文件的读取接口
.Capabilities 目标集群支持的 API 版本和 Kubernetes 版本
.Template 当前模板的路径信息

取字段时按对象层级写，比如 .Release.Namespace、.Values.image.tag、.Chart.Name。写兼容多集群的模板时，用 .Capabilities.APIVersions.Has 判断某个 API 版本是否可用；读取 Chart 内文件用 .Files.Get。

8.2. 作用域和 with

模板里的 . 代表当前作用域。顶层作用域挂着 Release、Values、Chart 这些对象，{{ .Values.name }} 的意思就是在当前作用域里找到 Values，再取 name。

with 可以把某个对象临时设为当前作用域。

进入 with 块以后，. 直接指向 .Values.people，取字段不用再写全路径。块结束以后作用域恢复。with 里面访问不到父作用域的对象，需要根作用域的值时用 $，$ 指向本次模板执行的根作用域。

8.3. if 和 range

if 按管道的结果决定是否渲染一段内容。

空字符串、数字 0、空列表、空字典、布尔 false 和 nil 在 Helm 里都算假。给字段设默认值常用 default。

range 用来遍历列表和字典。

每轮迭代里，. 指向当前元素。values 里的列表和字典都能遍历，模板里用 tuple 或 list 构造的集合也一样。

空白控制也值得记一下。{{- 和 -}} 会删掉紧邻的空白和换行，模板里常见行首写 {{-，避免渲染结果多出空行。中横线要贴紧大括号，{{- 3 }} 输出 3，{{-3 }} 输出 -3，少一个空格意思就变了。

9. 子模板和常用函数

Chart 变大以后，labels、annotations 这类片段会重复。Helm 用 define 定义子模板，用 include 或 template 引用。实际项目里子模板一般放在 templates/_helpers.tpl，以 _ 开头的文件不会被渲染成 Kubernetes 资源。

引用时把当前上下文传进去。

template 和 include 的区别在返回值。template 直接把子模板渲染到当前位置，结果不能继续接管道。include 返回字符串，可以接 nindent、quote 这些函数，实际项目里更常用。子模板名最好带 Chart 名前缀，避免和依赖的 Chart 撞名。helm create 生成的 _helpers.tpl 里已经有 <chart>.labels，自己加子模板时换一个名字，避免重复定义。多个 Chart 定义同名子模板时，后加载的会覆盖前面的，排查起来很费时间。

内置函数来自 Go 模板和 Sprig。字符串处理有 quote、upper、trim、trunc。给空值兜底可以用 default 和 coalesce。类型转换交给 atoi、toString，JSON 序列化用 toJson、toPrettyJson，正则匹配和替换用 regexMatch、regexReplaceAll，编码和哈希用 b64enc、sha256sum。日期处理是 now、date，dict 和 list 可以在模板里临时构造数据。完整函数表以 Sprig 文档 为准。

几个常用写法。

lookup 用来在渲染时查询集群里的现成资源。

lookup 在 install 和 upgrade 时能拿到真实数据，默认的 --dry-run 和 helm template 下返回空 map；--dry-run=server 会连集群，也能读到真实数据。模板里用 lookup 取集群里的值时，先用 with 或 if 判空，避免客户端 dry-run 时报空指针。

10. Release 的日常管理

Release 装好以后，日常操作集中在几条命令上。

命令 作用
helm list 列出当前 namespace 的 Release，加 -A 看全部
helm status 查看 Release 当前状态
helm get manifest 查看渲染后的完整清单
helm history 查看升级和回滚记录
helm rollback 回滚到指定 Revision
helm uninstall 卸载 Release 和它创建的资源

helm upgrade 每次执行都会让 Revision 加一。想省掉先判断再安装的步骤，可以用 --install。

prod-values.yaml 的内容按实际环境准备。

升级前先看历史，出问题回滚到指定 Revision。

rollback 本身也会产生一条新的 Revision，历史不会丢。卸载用 helm uninstall，加 --keep-history 可以保留记录，方便以后查。

11. 从仓库安装现成的 Chart

很多基础组件已经有现成的 Chart，直接装比自己写省事。以 Reloader 为例，它监听 ConfigMap 和 Secret 的变化，自动触发工作负载滚动更新。

先把仓库加到本地列表。

helm repo add 会把仓库索引下载到本地，helm repo update 用来刷新索引。装之前用 helm search repo 确认 Chart 名称和版本。私有仓库把地址换成自己的，需要认证时加 --username 和 --password。

Chart 的参数可以在安装或升级时覆盖。先看一眼默认 values，再决定改哪些。

12. 校验、打包和常见问题

Chart 写完先跑 helm lint，能提前发现 Chart.yaml 格式错误和模板语法问题。

lint 通过以后再 dry-run，最后打包。

打包会生成 mytest-0.1.0.tgz，版本号来自 Chart.yaml。这个包可以传到自己的 Chart 仓库，也可以作为依赖被别的 Chart 引用。

几个常见问题。

Chart.yaml 的大小写必须完全一致。文件名叫 chart.yaml 时，Helm 会报 Chart.yaml file is missing，把文件名改回来就行。

helm install 需要 Chart 路径，Release 名要么显式给出，要么加 --generate-name。只写 helm install 会报 requires at least 1 argument；写成 helm install mytest ./ 而当前目录不是 Chart 根目录，会报 Chart.yaml file is missing。

模板里定义子模板时带上 Chart 名前缀，避免多个依赖 Chart 出现同名 define。

values.yaml 不要提交明文密码。需要密钥时引用集群里已有的 Secret，或者用外部密钥管理工具注入，模板里只放引用。

如果只是想让第一个 Chart 跑起来，helm create 生成骨架，改一个模板，跑一次 dry-run 看看渲染结果；装进集群以后，再用 helm get manifest 核对实际提交的清单。后面遇到依赖、子模板和仓库，再回头查对应章节。
